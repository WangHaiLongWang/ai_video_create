# ai_video_create 长远路线图（v1.0 后 12-18 个月）

> 文档性质：**方向层**，不是执行计划。执行层见 [DELIVERY-PLAN.md](DELIVERY-PLAN.md) 与 [PLATFORM-HARDENING-PLAN.md](PLATFORM-HARDENING-PLAN.md)
> 基线日期：2026-10-12（对齐 [PROJECT-STATUS.md](../../PROJECT-STATUS.md) 状态版本 20.0）
> 读者：项目负责人、后续加入的开发者
> 排期原则：**门禁驱动，不写日历日期**。进入/出口条件未满足时，不得开下一班车
> 维护时机：每个版本出口门禁关闭、或出现影响路线的决策变更时校准

## 1. 现状与定位

### 1.1 产品一句话

**本地优先、单机、可视化 AI 视频流水线**：用户用节点和连线编排「提示词 → 分镜 → 图片 → 视频 → 合成」，平台负责编译、调度、恢复和资产血缘。

### 1.2 差异化能力（v1.0 之后继续加厚的护城河）

| 能力 | 说明 | 当前状态（2026-10-12） |
|---|---|---|
| **模块化节点** | BaseNodeKind 白名单 + 版本化 ModuleDefinition + 实例覆盖 | Phase M0-M3 完成，功能侧冻结 |
| **Workflow Agent** | 自然语言生成/修改工作流，GraphPatch 增量 diff 与破坏性确认 | v2 主链完成，v1 兼容待收口（HARD-401） |
| **可解释执行** | scene/variant 级血缘，最终视频可回溯到文本、图片、片段和模型参数 | 主链已通 |
| **本地优先** | 无 Docker/Redis/PostgreSQL/对象存储；Mock 全链路离线可跑 | 已满足 |

### 1.3 当前所处阶段

**功能完成、证据收敛**。综合完成度约 91%（PROJECT-STATUS §1），不是「还在盖功能」，而是「主链已通、缺发布级证据」。剩余阻断为 RC-004（同 SHA CI 证据）、RC-008（真实 Qwen/Wan3 当前证据）、RC-007（Doubao 外部阻断），全部由 [PLATFORM-HARDENING-PLAN.md](PLATFORM-HARDENING-PLAN.md) HARD-5xx 承接。

**路线图判断**：在证据收敛完成前，任何新功能开题都是错误决策——它会把「本机数字 ≠ 同 SHA CI 证据」的漂移源重新放大。下面的版本列车以 v1.0 发布为发车点，而不是以「下个月想做什么」为发车点。

## 2. 版本列车

> 读法：每班车给出**主题、用户价值、进入条件（Entry）、出口条件（Exit）、明确不做**。Entry 未满足时该版本不进入开发；Exit 未满足时不得发下一班车。版本号非最终，可在出口校准时按语义化版本规范微调（如 v1.1 拆为 v1.1/v1.2）。

### 2.0 列车总览

| 版本 | 主题一句话 | 发车前提（关键门禁） | 风险等级 |
|---|---|---|---|
| **v1.0.0-rc.x → v1.0.0** | 硬化收敛 + 真实 UAT + 发布演练 | Phase M3 完成（✅） | 低（不加功能） |
| **v1.0.x** | 安全补丁与协议漂移响应 | v1.0.0 已发布 | 低（只修不改） |
| **v1.1** | Provider 持久化 + 成本治理 + 可观测 | v1.0.0 稳定无阻断回归 | 中（涉及用户设置与费用承诺） |
| **v1.2** | 模板市场雏形 + 模块/Scene Bundle 复用 | HARD-101～104 共享契约落地 + v1.1 成本预估可用 | 中（分发格式影响兼容性） |
| **v2.0** | 平台化（多用户/云端/插件/分支循环/时间线） | 模块与契约稳定 + Provider 持久化 + 安全模型升级 + 真实团队需求 | 高（范围远大于 v1.x） |

**依赖关系摘要**：契约单一来源（3.1）是 v1.2 的硬前置；成本治理（v1.1）是「敢让用户批量跑」的前提；安全模型升级是 v2.0 的硬前置。**跳过前置直接开下一班车，是本路线图最需要防的错误。**

### 2.1 v1.0.0-rc.x → v1.0.0：硬化收敛与发布

| 项 | 内容 |
|---|---|
| **主题** | 把「功能完成」收敛为「可安装、可升级、可回滚、可复现」的正式版 |
| **用户价值** | 新用户按文档可从零装起；旧库升级不丢数据；付费调用前能预估成本；发布物可验证 |
| **对应工单** | HARD-501/502/503/504/505/506、HARD-601～604；关闭 RC-004/RC-008，明确 RC-007 状态 |
| **Entry** | Phase M3 已完成（✅ 满足）；工作区无未收敛的功能性变更 |
| **Exit** | 同 SHA 三平台 required checks 全绿并归档报告；MiMo/Qwen/Wan3 当前 commit 最小真实 UAT 通过（或 RC-008 明确移出范围并有用户可见说明）；安装/升级/回滚/备份恢复演练通过；`v1.0.0` tag 只指向已验证 SHA |

**范围冻结原则**：本列车内**只修 bug 与补证据，不加功能**。发现的设计缺陷若需要改行为，记入 §5 决策待定项或推入 v1.1，不在 RC 期「顺手加上」。

**明确不做**：任何新节点类型、新 Provider、新模块能力、UI 重做、性能优化项（除非它导致 RC 门禁失败）。

**Doubao 处置**：RC-007 为外部阻断（账号模型未激活）。**推荐：v1.0 明确降级为 Optional/External Blocked**，不进入必选门禁，但不得在发布说明中宣称其生产可用。理由见 §5.1。

### 2.2 v1.0.x 维护线：不引入风险的信任维持

| 项 | 内容 |
|---|---|
| **主题** | 安全补丁、Provider 协议漂移修复、文档与安装体验 |
| **用户价值** | 「装了就能一直用」，不被上游协议变更或安全通告打穿 |
| **Entry** | v1.0.0 已发布 |
| **Exit** | 无固定终点，随 v1.1 发车转入稳定分支维护 |
| **典型内容** | 依赖安全通告响应；Qwen/Wan3/MiMo 协议字段漂移的 Contract Test 修复；安装文档勘误；平台 smoke 失败修复；CHANGELOG/Known Issues 维护 |

**明确不做**：新功能、schema 不兼容变更、大范围重构。**每条补丁必须能在旧库上无损运行**——这是维护线的唯一硬约束。

### 2.3 v1.1 稳定与成本治理：能放心长期用、花钱可控

| 项 | 内容 |
|---|---|
| **主题** | Provider 配置产品化 + 成本可观测 + 执行可观测 |
| **用户价值** | 内容创作者可以连续出片而不用担心「改了设置重启就丢」「跑一次不知道花了多少」「失败了不知道怪谁」 |
| **对应工单** | HARD-301/302/303/304（Provider 持久化与秘密）、HARD-404 产品化（预算上限）、HARD-506 延伸的失败归因、HARD-403 审计 |
| **Entry** | v1.0.0 发布且维护线未发现阻断级回归；Provider 持久化（HARD-301～303）在硬化期已落地或有可复用半成品 |
| **Exit** | UI 保存的 Provider 设置重启恢复且回归测试覆盖；运行前有调用量/成本预估，超预算在提交前阻断；执行历史可按错误码归因、可看耗时分布；FFmpeg 安装检查与失败提示达到「新用户可自助排查」水平 |

**主题拆解（三件事，按此顺序）**：

1. **Provider 配置持久化收尾**：多 Provider CRUD、默认选择、测试连接、secret reference 轮换（AES-GCM 存储、GET 不回显）。Workflow/Module 只保存 provider config ID。
2. **成本治理产品化**：把 HARD-404 的「apply 前限额」升级为运行前预估（按 scene 数 × variant 数 × 单价）、预算上限、并发上限和历史花费视图。**没有这一步，批量出片功能本身就是成本事故源。**
3. **执行可观测性**：失败归因（Provider/网络/参数/资源）、耗时分布（P50/P95 per node kind）、可导出的执行报告。

**明确不做**：模板市场、跨项目资产复用、新 Provider、多用户。FFmpeg 若出现跨平台不可播放缺陷则升为 P0 修复，否则不重写合成管线。

### 2.4 v1.2 模板与可复用资产：少从零搭图

| 项 | 内容 |
|---|---|
| **主题** | 官方模板市场雏形、模块导入导出/跨项目复用、Scene Bundle 协作格式 |
| **用户价值** | 「打开就能用别人验证过的图」，而不是每次从空白画布开始；创作者之间可以交换分镜包而不是截图 |
| **对应能力** | 模板浏览/评分/一键应用；ModuleDefinition 导入导出（带版本与校验）；Scene Bundle 作为协作交换格式（Markdown/CSV/JSON 既有能力的产品化） |
| **Entry** | **HARD-101～104 共享契约已落地**（否则导入导出就是把漂移分发给用户）；v1.1 成本预估已可用（模板应用后立即可跑，用户需要先知道代价） |
| **Exit** | 官方模板 ≥ 一组可演示的完整链路（含滑雪教学验收形态）；模块导入导出 roundtrip 通过 parity test；Scene Bundle 在两台机器之间交换后可重新导入并执行 |

**明确不做**：第三方上传任意代码模块、用户生成内容审核体系、计费分成、云端模板托管。**模板分发 v1.2 仍是「文件交换 + 内置库」，不是 marketplace。**

### 2.5 v2.0 平台化：PRD §9「不做」清单转正

| 项 | 内容 |
|---|---|
| **主题** | 从单机工具升级为可协作平台 |
| **候选范围** | 多用户/RBAC、云端部署、插件或沙箱扩展、条件分支/循环、专业时间线与音轨 |
| **用户价值** | 团队共用工作流与资产；复杂叙事结构（分支结局、循环分镜）；接近成片的剪辑能力 |
| **Entry** | 模块与契约体系稳定（v1.2 出口）；Provider 配置持久化与成本治理稳定（v1.1 出口）；**安全模型升级完成**（当前单机 127.0.0.1 模型不适用于多用户）；有真实团队用户需求证据，而不是想象出来的 |
| **Exit** | 待定——进入 v2.0 规划时另立计划文档 |

**明确不做（本轮再排除）**：为所有云厂商提供专用适配器（PRD §9 原文，继续有效）；实时多人同时编辑同一画布（协作以工作流/资产共享为先，不做 CRDT）。

**路线图判断**：v2.0 范围远大于 v1.x 之和，**不应在单人维护、证据体系未建立的前提下启动**。若 v1.1/v1.2 期间出现付费团队客户或明确采购需求，优先做「多用户 + 权限」，插件沙箱与专业时间线可再拆分为 v2.1/v2.2。

## 3. 工程支柱（跨版本持续投入）

> 六根支柱不是版本功能，是**每个版本都要还的债**。每根给出：现状 → 目标 → 迭代动作。版本列车负责「做什么」，支柱负责「不腐烂」。

### 3.1 契约单一来源（当前最大漂移源）

| 项 | 内容 |
|---|---|
| **现状** | Node Manifest / ModuleDefinition / WorkflowSpec / Agent Catalog 仍有多份实现（前端 `node-manifest.ts`、后端 `node_manifest.py`、`_NODE_CATALOG_V2`、`workflow_factory.NODE_DEFS`、Agent label map 等）。Phase M3 已修掉一批具体漂移（如 `imageToVideo` 输出基数），但**机制未变，漂移会复发** |
| **目标** | `schemas/` 为唯一事实来源；TS 与 Pydantic 由 schema 生成或加载；parity test 在 CI 中自动阻断漂移 |
| **迭代动作** | HARD-101 冻结 base-node-manifest → HARD-102 module/workflow schema + roundtrip fixture → HARD-103 生成 Catalog、删手写表 → HARD-104 Agent 只消费共享 Catalog。v1.1 起：新增节点/端口必须先改 schema，禁止绕过生成物提交 |

### 3.2 数据与迁移

| 项 | 内容 |
|---|---|
| **现状** | 按 SQL 文件启动执行，依赖重复列容错，**缺 `schema_migrations` 账本与 checksum**；旧库升级与中断恢复无正式证据 |
| **目标** | 每个迁移只执行一次且可追溯；checksum mismatch 显式失败；旧库无损升级；中断不留半迁移状态 |
| **迭代动作** | HARD-201 ledger + 事务化 runner → HARD-202 001-011 baseline 识别 → HARD-203 中断/损坏备份测试 → HARD-204 module_usage/scene drafts 回归。v1.1 起：任何 schema 变更必须附「空库 / 旧库 / 中断恢复」三件套测试 |

### 3.3 证据体系（反复出现的「本机 ≠ CI」）

| 项 | 内容 |
|---|---|
| **现状** | 多轮校准反复出现「本机数字 ≠ 同 SHA CI 证据」（PROJECT-STATUS §2 明确标注待复证）；能力与证据层级脱节，读者无法判断「这项能力被测到什么程度」 |
| **目标** | **能力↔证据矩阵**：每项能力标注 unit / integration / browser / real-UAT 覆盖层级，缺口可视化；测试数字一律绑定 SHA 与环境 |
| **迭代动作** | v1.0 出口前建立矩阵初版（可从 PROJECT-STATUS §1 评分表扩展）；v1.1 把矩阵纳入 CI 产物；v1.2 起新能力无对应证据层级标注不得合并 |

### 3.4 Provider 治理

| 项 | 内容 |
|---|---|
| **现状** | Doubao 外部阻断（RC-007）；Qwen/Wan3 仅有历史证据（RC-008）；Settings API 主要改内存，重启回退 `.env`；无故障演练常态化 |
| **目标** | 多 Provider 配置持久化；协议 Contract Test 常绿；故障演练（429/timeout/cancel）不产生假成功资产；成本上限可配置 |
| **迭代动作** | HARD-301～304 持久化 → HARD-506 故障演练 → v1.1 成本上限产品化 → v1.2 起每个 Provider 发布前必须过 Contract Test + 一条最小真实链路（manual/nightly，非 PR 默认门禁） |

### 3.5 安全与秘密

| 项 | 内容 |
|---|---|
| **现状** | 安全代码已存在（Rate Limit、SSRF、审计日志、AES-GCM 秘密存储、Secrets Scanner），完成度评分 83%；**依赖环境与发布证据仍需修复**；鉴权模型是单机 127.0.0.1 假设 |
| **目标** | 秘密存储 AES-GCM + 不回显 + 可轮换，有测试证据；日志/导出/错误详情零泄漏；**为 v2.0 多用户预留鉴权边界**（API 层与领域层分离，避免 v2.0 重写） |
| **迭代动作** | HARD-302 秘密持久化与轮换 → 发布演练中的安全报告归档（HARD-502）→ v1.1 起 secret 轮换有操作手册 → v2.0 前完成威胁建模（多用户场景下 SSRF/资源隔离/审计） |

### 3.6 可维护性

| 项 | 内容 |
|---|---|
| **现状** | 前后端 + E2E 规模已不小（后端 non-external 2123 passed 量级）；存在死代码（如曾复活的 `PatchPreview`）、warning 未清、测试时长随用例增长、文档多处需防漂移 |
| **目标** | 死代码定期清理；测试时长有预算并被监控；文档与代码同步规则可执行（状态/计划/PRD 分层已在 docs/README.md 治理章节固化，需坚持） |
| **迭代动作** | HARD-003 清理 warning → v1.1 统计并设测试时长预算 → 每个版本出口做一次死代码/未用导出清理 → 文档冲突按 §6 优先级规则处理，禁止「代码里改了行为文档不动」 |

## 4. 风险与对冲

PRD §10 的产品风险继续有效（SQLite 写竞争、长任务重复计费、协议变化、磁盘耗尽、FFmpeg 差异、Agent 非法图、API 成本）。以下是**长期视角**的增量风险：

| 风险 | 影响 | 长期对冲 | 归属支柱 |
|---|---|---|---|
| **外部模型激活不确定**（Doubao 已现实发生） | 某条产品线长期无法真实验收 | Provider 保持可选；发布说明明确能力边界；不把单一厂商写入必选门禁 | 3.4 |
| **Provider API 持续变更** | 已发布用户升级后链路断裂 | Contract Test 常绿 + 错误归一化 + 版本锁定；维护线设协议漂移响应 SLA（目标：通告后一个维护窗口内修复） | 3.4 |
| **单人维护瓶颈** | 关键知识集中、休假/离职即停摆 | ADR 与运行手册（DELIVERY-PLAN §15 已要求）；支柱 3.1/3.2 把「隐性知识」变成测试与迁移账本；v1.2 前至少两人能独立完成发布演练 | 3.6 |
| **SQLite 上限** | 多执行并发、资产表膨胀后写竞争或备份变慢 | 短事务 + WAL + 原子 claim 维持；**在 v1.1 观测耗时分布时同步监控 DB 时延**；触发阈值时评估拆库或迁移，不在 v2.0 前主动换库 | 3.2 |
| **成本失控** | 用户批量出片后账单事故，伤害产品信任 | v1.1 成本预估与预算上限为**发车条件而非增强项**；真实 Provider job 保持 manual/nightly 并设调用量上限 | 3.4 |
| **证据再次漂移** | 再次出现「本机全绿、CI 无证据」的 RC 循环 | 能力↔证据矩阵强制化；RC 证据只认同 SHA 产物 | 3.3 |
| **范围蠕变**（路线图自身的风险） | 版本列车永远发不了车 | 每车「明确不做」清单；Entry 未满足不开工；决策悬而未决时先写入 §5 而不是先写代码 | 3.6 |

## 5. 决策待定项（需要负责人拍板）

> 以下决策影响路线走向，当前文档中悬而未决。每条给出选项与**推荐倾向**。拍板后应更新本表并同步 PLATFORM-HARDENING-PLAN 对应工单。

### 5.1 v1.0 是否包含 Doubao

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 必选门禁 | 未激活则 v1.0 不能发 | 发布被外部账号状态绑架，工期不可控 |
| B. Optional / External Blocked（**推荐**） | 发布说明写明「Doubao 模块已实现，模型激活后启用」，不进必选门禁 | 功能存在但不承诺可用；需清晰的用户可见说明 |
| C. 移出 v1.0 | 代码保留但文档不提及 | 丢掉已投入的 Seedream 模块纵向能力展示 |

**推荐倾向：B**。理由：RC-007 是外部阻断，不应进入工程关键路径；已有的 Seedream 模块样板（`builtin.seedream.text-to-image`）是差异化能力的演示载体，删掉可惜；但绝不能在发布说明中宣称生产可用（PLATFORM-HARDENING-PLAN §11 与 DOUBAO-SEEDANCE-PLAN 已同此口径）。

### 5.2 Agent v1 是否下线（HARD-401）

| 选项 | 含义 | 代价 |
|---|---|---|
| A. v1.0 直接删除 | API/前端只留 v2 | 可能破坏已有脚本/习惯；无迁移窗口 |
| B. v1.0 标记弃用 + 迁移窗口，v1.1 移除（**推荐**） | v1 返回弃用响应与迁移指引 | 短期双轨成本（已存在） |
| C. 无限期双轨 | 保持现状 | acceptance 行为不一致问题永久化 |

**推荐倾向：B**。理由：PROJECT-STATUS §4 已记录「v1 与 v2 acceptance 行为不一致」是架构债务；直接删除风险在于没有用户告知渠道，无限期双轨则持续消耗测试与心智。弃用响应 + 一个小版本窗口是成本最低的收口方式。HARD-401 工作量本身仅 0.5d，**该决策真正的成本是双轨测试，而不是代码**。

### 5.3 image-only 终点形态（HARD-402）

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 通用 AssetOutput 节点 | 任意资产类型终点，语义统一 | 需要定义多类型输出的展示与下载规则 |
| B. 明确终端节点（按资产类型） | image→ImageOutput、video→VideoOutput | 节点种类增加，但语义直白 |
| C. 保持隐式（无 output 也可结束） | 现状 | 血缘/产物边界模糊，Agent 与校验器各有理解 |

**推荐倾向：A**。理由：一个类型化 AssetOutput 能同时覆盖 image-only、video-only 与混合场景，避免节点种类翻倍；且与「输出：任意资产」的 PRD 4.2 表述一致。代价是 PropertyPanel 需要按资产类型分支展示——这在 ModuleDefinition Schema 驱动下是可承受的。**但若负责人更看重「新手一眼看懂」，B 也是可辩护的选择**；C 明确不推荐，它是当前隐式语义漂移的根源。

### 5.4 Scene JSON roundtrip required checks 的纳入时点

| 选项 | 含义 | 代价 |
|---|---|---|
| A. v1.0 RC 期纳入 required（**推荐**） | SCENE-010（历史 RC-003C）随 HARD-501/502 一并关闭 | RC 期多一项门禁，可能暴露缺陷 |
| B. v1.0.x 维护线纳入 | 先发后补 | 发布时存在已知 skip，用户导入导出无 CI 保障 |
| C. v1.1 | 与模板工作一起做 | 长期 skip 损害「可复现」承诺 |

**推荐倾向：A**。理由：PRD 4.1 将「导入导出 roundtrip 结构等价」列为编辑器验收项，KNOWN-ISSUES 也已登记该 skip；它是**用户数据完整性**相关门禁，不是增强功能。当前 Playwright 全量中唯一 skip 就是它，纳入成本相对可控。若 RC 期暴露实现缺陷且修复超出范围，再降级为 B 并在 Known Issues 中显式记录。

### 5.5 是否引入 monorepo 工具/包边界

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 维持现状（人肉对齐前后端契约） | 零迁移成本 | 漂移复发风险由支柱 3.1 的 parity test 兜底 |
| B. 轻量共享包（如 `packages/contracts` 仅放 schema/生成物）（**推荐**） | 前后端从同一包消费 | 引入 workspace 工具链；安装/CI 略复杂 |
| C. 完整 monorepo（Nx/Turborepo 等） | 统一构建、任务编排 | 对单机单产品项目过重；学习与维护成本高 |

**推荐倾向：B，且时机放在 HARD-101～104 收口时**。理由：HARD-103 本来就要「生成 Catalog、删手写重复表」，把生成物放进一个共享目录/包是顺手的边界收束；完整 monorepo 工具（C）在单人维护下收益不抵成本，明确不做。若 HARD-101～104 仅靠 parity test 就足够阻断漂移，A 也可接受——**关键是 parity test 必须存在，工具只是手段**。

### 5.6 拍板后的处理约定

1. 每项决策更新本节表格状态（推荐 → 已采纳/已否决），并注明采纳日期（由负责人填写，不预设）。
2. 影响工单范围的，同步 PLATFORM-HARDENING-PLAN 对应 HARD 条目；影响用户承诺的，先改 PRD 再改计划（DELIVERY-PLAN §15 既有规则）。
3. 决策未拍板前，相关工单**不得以「先按某个选项做起来」为由开工**。

## 6. 与其他文档的关系

### 6.1 文档分层

| 层 | 文档 | 职责 | 不负责 |
|---|---|---|---|
| **方向层** | 本文件 ROADMAP.md | 版本主题、进入/出口门禁、工程支柱、长期风险、待决策项 | 具体工单、工作量、测试数字 |
| **执行层** | [DELIVERY-PLAN.md](DELIVERY-PLAN.md)（主交付）、[PLATFORM-HARDENING-PLAN.md](PLATFORM-HARDENING-PLAN.md)（当前推进主线） | Sprint、工单 ID、工作量、验收标准、DoD | 版本主题取舍、跨版本方向 |
| **状态层** | [PROJECT-STATUS.md](../../PROJECT-STATUS.md) | 完成度、可重复测试基线、发布阻断登记 | 排期、产品方向 |
| **产品层** | [product/PRD.md](../../product/PRD.md) | v1.0 用户价值、范围、验收、风险 | 实现百分比、短期任务 |

其余专项计划（SKI-LESSON、DOUBAO-SEEDANCE、MODULAR-NODE-SEEDREAM 等）属执行层子计划，服务于当前版本列车，不改变方向层结论。

### 6.2 冲突优先级

1. **事实冲突**（完成度、测试数字、阻断状态）：以 **PROJECT-STATUS.md** 为准；本文件只引用不复制数字。
2. **范围冲突**（这个版本做什么/不做什么）：以 **ROADMAP.md** 为准；执行层不得私自扩大版本范围。
3. **执行冲突**（工单顺序、验收标准、Sprint 排期）：Sprint 排期与硬化执行以 **PLATFORM-HARDENING-PLAN** 为准，交付范围与发布门禁以 **DELIVERY-PLAN** 为准（与 docs/plans/README.md 既有约定一致）。
4. **需求冲突**（用户价值、验收口径）：以 **PRD** 为准；先由负责人更新 PRD，再调整 ROADMAP 与执行计划。
5. 任何层级与 Superseded/历史报告冲突时，**历史文档不生效**，只作追溯。

### 6.3 本文件的维护边界

- ROADMAP **不用于领取工单**。可执行任务一律出自 DELIVERY-PLAN / PLATFORM-HARDENING-PLAN。
- 版本出口门禁关闭后，应在本文件对应章节追加「出口已满足」标注与指向证据的链接（证据本身写 `reports/`，不写在本文件）。
- 出现影响版本列车的决策或外部变化（如 Provider 商业条款、模型激活）时校准；**不因单个工单完成而改写方向**。
